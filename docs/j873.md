# J873g / T8152 firmware preparation

Branch `j873` starts from M5/J813 commit
`69534d4899e20108d2c7a085565a7097509fa17f`. No M6 hardware is available.

Apple's macOS 27.0 RC `26A428` root BuildManifest and
`Firmware/all_flash/DeviceTree.j873gap.im4p` confirm `Mac18,5`, `J873gAP`,
chip ID `0x8152`, and board ID `0x24`. The IM4P SHA-384 digest matches the
manifest. The separate `j873sap` tree is T6050 and is not the M6 target.

The raw M6 ADT is 614344 bytes, SHA-256
`3252a3f13dc025ffa8551c7a5da6a71501f76ea6c5d38aa35390f9268a6dc378`.
It now rebuilds byte-for-byte through the normal `load_adt()` API. PMGR2 and
incomplete PMGR trees load without invoking PMGR1 helpers, which explicitly
reject unsupported layouts. Legacy PMGR initialization no longer inserts an
unintended `pmgr-u8id` property into serialized ADTs. Multi-entry `service-gates`
properties decode as individual 32-bit IDs, including eight-byte lists.

## Verified static differences from J813

- T8152 UART0: translated address `0x331200000`, size `0x4000`.
- AIC: `aic,3`, translated address `0x301000000`, size `0x1cc000`.
- PMGR: `/arm-io/pmgr-child` is `pmgr2,t8152`; register zero translates to
  `0x300700000`. `/arm-io/pmgr` has no `reg` property.
- UART uses `service-gates` instead of the J813 `clock-gates` property.
- DART: `dart,gen3`; USB0 DART starts at `0x403020000`.
- ANS and GPU ASC wrappers: `iop,ascwrap-v8`; ANS register zero is
  `0x321600000`, size `0x74000`.
- The ADT has 12 CPU descriptors: 6 E, 2 P, 4 M. This is a firmware topology,
  not proof of enabled CPU count or CPU initialization sequences.

These addresses include ADT bus-range translation. Do not use raw child `reg`
values as physical MMIO addresses. Common compatible strings are not proof that
all M5 programming sequences are valid on T8152.

## Offline implementation

`proxyclient/m1n1/pmgr2.py` decodes the evidenced 48-byte device, 36-byte service,
and 12-byte power-group records. It resolves all 352 device registers within
their translated ADT windows. There are 170 implicit service IDs and 21 explicit
service definitions. Implicit names come from the runtime PMS interface; they
must not be guessed by looking up the same numeric device ID. The module never
performs MMIO or sends a power-service request.

`proxyclient/m1n1/asc_v8.py` describes the postoffice mailbox register offsets and
status fields derived from AppleMessageBoxMailbox in the 26A428 ASCWrap-v8
driver. Callers provide the aperture explicitly. Its 0..255 mailbox input bound
is a conservative tooling bound, not a measured hardware mailbox count. This
is an offline layout helper, not an ASC transport or RTKit driver.

The strict J873g identity helper checks chip, board, model, root target type and
the exact compatible list. T8152 has its own early-UART address definition; it
is not aliased to T8142.

## Opt-in first-entry diagnostic

```sh
git submodule update --init artwork
make -j8 BUILD_DIR=build-j873-diagnostic EXTRA_CFLAGS=-DJ873_DIAGNOSTIC
```

Do not add `TARGET`: the diagnostic deliberately disables assembly UART writes
before identity validation. Its C entry runs after relocation/BSS initialization
and before normal initialization. An exact J873g identity permits adoption of
the existing UART, prints architectural CPU ID registers, boot arguments, and
CPU states, then halts. Wrong identities halt without accessing the UART. It
does not initialize CPU implementation registers, MMU, dockchannel, AIC, PMGR,
watchdog, USB, storage, secondary CPUs, payloads or proxy transport. EL3 entry
stops before attempting a transition. The watchdog may still reboot a real
device; its M6 programming sequence is unverified.

The Mach-O and raw images build successfully. They are experimental first-entry
artifacts, not installer payloads. The iBoot entry ABI, live UART readiness,
cache state, and actual M6 register access have not been tested. Keep any future
known-good resident image and use temporary chainloads for initial tests.

## Reproduce tests

Use an isolated Python environment with `requirements.txt`, `pytest`,
`unicorn`, and `pyelftools` installed:

```sh
../.venv/bin/python -m pytest -q tests/python/test_adt_pmgr.py tests/python/test_j873_tables.py
sh tests/platform_identity/run-host-tests.sh
../.venv/bin/python tests/python/run_j873_diagnostic_emulated.py \
  build-j873-diagnostic/m1n1.elf \
  --adt ../firmware/26A428/26A428__MacOS/DeviceTree.j873gap.bin
```

The instruction harness executes the linked ELF from `_start`, with synthetic
RAM, CPU registers and UART status. It tests EL1 and EL2 success, wrong-chip,
wrong-board and truncated-identity rejection, and a firmware-derived ADT. That
last fixture sets synthetic runtime chip/board IDs and clears firmware template
length flags; it is not an unmodified live ADT. Unexpected MMIO and entry into
normal platform initializers fail the test. The harness caught a last-CPU
iteration bug in the diagnostic, now fixed. Passing does not model M6 silicon,
interrupt delivery, power management, SPTM, DMA or cache behavior.

Normal/reference builds compile separately with
`make BUILD_DIR=build-j873-reference`. Compilation is not M6 boot support.

The sibling AuroraSilicon repository contains the detailed evidence in
`targets/j873/firmware-evidence.json`, acquisition instructions in
`targets/j873/README.md`, and `tools/inspect-j873-firmware.py` for offline checks.
The local raw files are in `../firmware/26A428/26A428__MacOS`.
